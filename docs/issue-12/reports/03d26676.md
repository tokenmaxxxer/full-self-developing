### Proposed design

1. `_require_must_first(n, branch, text)` — parse `## Must first` from
   docs/specs/northpole.md into bullets (joining continuation lines that don't start
   with `-`, dropping the `since/revised` line). For each bullet, it counts as "claimed
   satisfied" if a majority of the bullet's significant words (lowercased, stopwords
   dropped) appear either (a) in the record's `## Acceptance verification` or
   `## Judgment` sections, or (b) in the issue's own body (title + `## Problem` +
   `## Acceptance`) fetched via `issue_view(n)`. (b) is what keeps the check from
   blocking the very issue meant to satisfy a Must-first item: such an issue's own
   Problem/Acceptance text is what states the item, so the gate never demands the
   record additionally recite it. Any bullet claimed by neither refuses, printing the
   bullet's text.

2. `_require_watch_for_evidence(n, text)` — read `## Watch for` from the *issue* body
   (`issue_view(n)["body"]`), not the north pole (the acceptance text says "the issue's
   own `## Watch for` list"). For each bullet, require a line in the record's
   `## Evidence` section whose text overlaps the bullet's significant words (same
   overlap test as above). Missing → refuse, printing the bullet's text. An issue with
   no `## Watch for` section is not checked (nothing to be evidenced).

3. `_require_reason_for_unrequested_files(n, branch, text)` — `git diff --name-only
   {MAIN}...{branch}`, filtered to files that are either newly added
   (`git diff --diff-filter=A --name-only`) or match the `minimal-change` decision's own
   globs (`.github/**`, `**/ci/**`, `**/deploy/**`, `**/*.yml`, `**/*.yaml`) or a
   test-infrastructure pattern (`**/test/**`, `**/tests/**`, `**/*_test.*`,
   `**/*.test.*`, `**/*.spec.*`, `**/conftest.py`) not literally named in the issue's
   `## Acceptance` section. If any such path exists and the record's `## Judgment`
   section is empty or exactly `none`, refuse and list the paths — reusing
   `minimal-change`'s own scope globs rather than inventing a second list.

All three run inside `cmd_accept`, same place for `--via delegation` (the acceptance
text: "`--via delegation` behaves the same"), each printing every unmet condition in one
pass (not one refusal per turn) and `sys.exit`-ing non-zero, matching the existing
`_require_principles`/`_lint_on_branch` style already in the file. None of the three
forbid a file kind or a missing item outright — they refuse only for a missing
*reason/claim*, per the issue's own "Watch for" line.

## Judgment

Methods considered for matching a north-pole/issue bullet to record text:
- Exact substring/phrase match of the bullet against the record — rejected: the north
  pole's prose is hand-written and wraps across lines; a record that paraphrases a
  Must-first item (which is normal — the record isn't required to quote the north pole)
  would false-refuse, and the acceptance text requires refusals to name a real gap, not
  a formatting mismatch.
- A new structured tag the record must emit (e.g. a `must-first` frontmatter field) —
  rejected: issue's own Watch for says "do not invent a new config format: the gate
  reads docs/specs/northpole.md and the issue/record as they are." A new required tag
  is exactly such a format, and it would also fail today's already-published records
  that predate this issue.
- (smallest) Word-overlap over the bullet's significant words, read out of the sections
  that already exist (`## Evidence`, `## Judgment`, `## Acceptance verification`, the
  issue body) — chosen. It adds no new file, no new frontmatter, and no new markdown
  section; it reuses `find_section`/`extract_section`, already imported in otr.py, and
  the `minimal-change` decision's own glob list for the third check instead of a second
  list. Decided by Priority #3 (the smallest change that solves the stated problem) and
  by the issue's own Watch for line against inventing a new config format.

The "must not block the very issue meant to satisfy Must first" line decided the
issue-body fallback in check 1: an issue whose own Problem/Acceptance states a
Must-first item satisfies the gate through that text, so the gate can never demand the
record additionally restate what the issue itself already commits to — a self-reference
loop was rejected because Priority #3 and the Watch-for line both push toward reading
what already exists rather than adding a re-statement requirement.
