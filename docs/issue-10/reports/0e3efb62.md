# issue-10 — 0e3efb62 record

## What was done

Delivered exactly the plan from this record's proposal phase (superseded in place, same
file, per RECORD instructions — no other record was written):

1. Removed the dead `ISSUE_BODY` template constant from `plugin/tools/otr.py`
   (`## Need` / `## Acceptance` / `## Out of scope` string, never referenced by
   `cmd_issue` or anything else) — its presence modeled exactly the shape this issue
   moves away from.
2. Added `## Acceptance` and `## Out of scope` sections to `plugin/templates/record.md`,
   between `## Principles` and `## Deviations`.
3. Added a `record_lint.py` check: a `type: proposal` record needs a non-empty
   `## Acceptance` section (reusing the existing `_section_has_content` helper, same
   pattern as the `## Evidence` and `## Acceptance verification` checks already there).
4. Added `record_body_of`, `extract_section`, `set_section` to `otr.py` and wired
   `cmd_approve` to read the record's `## Acceptance` / `## Out of scope`, merge each
   non-empty one into the current issue body (`gh issue edit`, in place if the header
   already exists, appended otherwise), and append `Wrote Acceptance, Out of scope from
   the record into the issue body.` (or just the section(s) actually written) to the
   `APPROVE` comment. When the record supplies neither section (e.g. a delivery-type
   record with nothing new to say), the issue body — and any human-written Acceptance —
   is left untouched, satisfying the Watch-for line about not silently rewriting a
   human's own Acceptance.
5. Reworded `PHASE_RULES["proposal"]` to ask for `## Acceptance` / `## Out of scope` in
   the record (propose if the issue has none, keep-or-refine and say which if it does)
   instead of presupposing the issue already has Acceptance items to walk through; and
   `PHASE_RULES["delivery"]` to say "every item in the issue's current `## Acceptance`
   section" instead of the unqualified "every Acceptance item" — since `cmd_directive`
   already re-fetches `issue_view(n)` live (unchanged), the delivery directive text now
   correctly points at the Acceptance the human approved via change 4, with no further
   code change needed in `cmd_directive`.

Deviation from the proposal (recorded under ## Deviations, not silently fixed): while
implementing 2–4 I found that a plain substring search for `"## Acceptance"` inside a
record body also matches inside `"## Acceptance verification"`, because the shorter
header is a text prefix of the longer one. This affects both the new `record_lint`
proposal check and the new `cmd_approve` extraction — for the lint check, a proposal
record with only the template's empty `## Acceptance verification` placeholder (no real
`## Acceptance` section at all) would have been read as "has Acceptance content" using
the trailing text of `## Acceptance verification`'s own body, letting the check pass
incorrectly. I fixed it in the same commit with a line-anchored `find_section()` (regex
`^## Acceptance$` as its own line) used everywhere a header is now looked up, since
leaving a check that silently doesn't check anything is worse than the smaller collision
fix.
