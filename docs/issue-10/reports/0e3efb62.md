# issue-10 — 0e3efb62 record

## What was done

Read `plugin/tools/otr.py` (`cmd_issue`, `DIRECTIVE`, `PHASE_RULES`, `cmd_directive`,
`cmd_approve`), `plugin/tools/record_lint.py`, and `plugin/templates/record.md` to see
where the Need/Acceptance/Out-of-scope shape and the "Acceptance item of the issue"
language currently live, then designed the smallest set of edits that implement the
Problem/Watch-for split (delivery phase — implementation only, no code changed here):

1. **`otr issue` (no functional change).** `cmd_issue` already writes `a.body` to GitHub
   verbatim (`gh("issue", "create", ..., "--body", body)`) — it has never enforced a
   shape, so a body containing only `## Problem` and `## Watch for` already creates
   today. The only thing to remove is the dead `ISSUE_BODY` template constant
   (`otr.py:180-192`, the `## Need` / `## Acceptance` / `## Out of scope` string) — it is
   never referenced by `cmd_issue` or anything else (confirmed by `grep -n ISSUE_BODY`
   below), and its survival models exactly the shape this issue moves away from. Removing
   it is in scope of "smallest change that solves the stated problem" because leaving it
   is actively misleading about what shape an issue must have, not because it does
   anything.

2. **`plugin/templates/record.md`.** Add two sections between `## Principles` and
   `## Deviations`:
   ```
   ## Acceptance

   <If the issue already has an ## Acceptance section, keep or refine it here and say
   which. If not, propose one. Required non-empty on a proposal record.>

   ## Out of scope

   <Same as above. May be empty if the proposal has nothing to exclude.>
   ```
   These are the sections `otr approve` reads (item 4).

3. **`record_lint.py`.** Add one conditional check alongside the existing
   `REQUIRED_SECTIONS` / terminal-record checks: when `fm.get("type") == "proposal"`,
   require `_section_has_content(body, "## Acceptance")` (same helper already used for
   `## Acceptance verification` and `## Evidence`), erroring `"proposal record needs a
   non-empty ## Acceptance section"` otherwise. `## Out of scope` is not required
   non-empty — a proposal legitimately may have nothing to exclude. No change to the
   existing terminal-record `## Acceptance verification` check: that one is already
   purely structural (section present and non-empty) and never needed to know what the
   issue's Acceptance text says, so item 4 of the issue ("record_lint treats Acceptance
   items as the issue body's current ## Acceptance after approval") is satisfied by the
   directive wording change in item 5, not by teaching record_lint to fetch the issue
   over `gh` — record_lint takes only a local path and must stay usable offline in
   `_lint_on_branch`'s detached worktree.

4. **`cmd_approve` in `otr.py`.** After `require_approver()` and the existing "nothing
   published" guard, read the record body (reuse `frontmatter_of`'s parser, which already
   splits frontmatter/body — add a one-line `record_body_of(text)` wrapper around
   `parse_frontmatter` that returns the body half), extract `## Acceptance` and
   `## Out of scope` with a small `extract_section(body, header)` helper (find header,
   take up to the next `\n## ` or end, `.strip()`), and if either is non-empty, merge it
   into the current issue body with a matching `set_section(body, header, content)`
   helper (replace the section in place if the header already exists, else append it),
   then `gh("issue", "edit", str(a.issue), "--body", new_body)` before posting the
   `APPROVE` comment. The APPROVE comment gets a line naming which sections were written,
   e.g. `Wrote Acceptance, Out of scope into the issue body.` — satisfying "says so in the
   APPROVE comment". If the record has no `## Acceptance` content (shouldn't happen once
   record_lint gates it, but `otr approve` itself does not call record_lint, so it is
   defensive) neither section is touched and the issue body is left as the human wrote
   it — this is also how a human-authored `## Acceptance` that the proposal chose not to
   touch survives unchanged (issue's Watch-for: "do not silently rewrite a human's own
   Acceptance if they did write one").

5. **`DIRECTIVE` / `PHASE_RULES` in `otr.py`.**
   - Proposal phase, replace "how each Acceptance item of the issue will be verified"
     (which presumes Acceptance already exists) with: "put a proposed `## Acceptance`
     and `## Out of scope` in your record (`plugin/templates/record.md` has the
     sections); if the issue already has them, keep or refine them there and say which;
     say how each Acceptance item will be verified."
   - Delivery phase, replace "covering every Acceptance item" with "covering every item
     in the issue's current `## Acceptance` section" — since `cmd_directive` already
     re-fetches `issue_view(n)` live for the delivery directive (`otr.py:291`), this
     text will, after `otr approve` lands change 4, be the Acceptance the human approved,
     with no further code change needed in `cmd_directive` itself.
