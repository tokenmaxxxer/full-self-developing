# issue-11 — a3066269 record

## What was done

- `plugin/templates/record.md`: inserted a `## Judgment` section between
  `## Principles` and `## Acceptance`, with the placeholder text spelling out the
  required shape — methods considered one line each, the smallest marked
  `(smallest)`, the one chosen, why (naming a Priority or Watch for item), or `none`
  if only one method was ever possible.
- `plugin/tools/record_lint.py`:
  - factored `_section_has_content` on top of a new `_section_content` helper (no
    behaviour change for existing callers).
  - added `_judgment_errors(body)`: if `## Judgment`'s content (stripped) is empty or
    literally `none` (case-insensitive), no error. Otherwise it collects the section's
    `-`-prefixed lines as "methods"; if there is more than one and none contains the
    literal `(smallest)`, it reports one error.
  - `lint_record` now also requires a non-empty `## Judgment` when `type == "proposal"`
    (mirrors the existing `## Acceptance` proposal-only rule) and always runs
    `_judgment_errors`.
- `plugin/tools/otr.py`:
  - `PHASE_RULES["proposal"]` gained a bullet telling the subagent to fill
    `## Judgment` (methods, smallest marked, chosen, why — or `none`).
  - `PHASE_RULES["delivery"]` gained a bullet telling the subagent to update
    `## Judgment` if delivery changed the chosen method, otherwise carry it over
    unchanged.
  - `cmd_publish` now extracts `## Judgment` from the record body (via the existing
    `extract_section` helper) and puts it in the PR body under a `**Judgment**`
    heading, right after the verdict line, before the `Record:` path line.

## Judgment

- One `## Judgment` section in `plugin/templates/record.md`, one lint rule in
  `record_lint.py`, directive wording in `otr.py`, PR-body line in `cmd_publish`
  (smallest) — reuses the existing `_section_has_content`/`extract_section`/
  `find_section` machinery already used for `## Acceptance` and `## Deviations`; adds
  no new parsing concept.
- A structured Judgment (YAML list of `{method, smallest: bool}` under frontmatter,
  or a separate per-issue judgment file) — rejected: the issue's own Watch
  for item says "Keep the section short by design... Do not turn it into a design
  document," and Priority 3 (smallest change that solves the stated problem) rules
  out a new file format or a frontmatter schema change when a markdown section with a
  one-line convention (`(smallest)`) does the same job with no new machinery.

Chosen: the markdown-section-plus-one-marker approach, because it is the smallest
change that gives `record_lint` something mechanical to check (a `(smallest)` string
match) while keeping the section human-writable prose, per Priority 3 and the issue's
own Watch for constraint against turning this into a design document.
